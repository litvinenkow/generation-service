# Generation service

Асинхронный сервис генерации на FastAPI и PostgreSQL. Compose поднимает PostgreSQL, API в четырёх Uvicorn worker-процессах и два тестовых провайдера.

## Запуск

```sh
docker compose up --build
```

API доступно на `http://localhost:8000`. Демо начисление:

```sh
python -c "import json,hmac,hashlib,urllib.request; b=json.dumps({'payment_id':'demo-1','user_id':1,'tokens':100,'status':'paid'},separators=(',',':')).encode(); r=urllib.request.Request('http://localhost:8000/webhooks/payments',data=b,headers={'Content-Type':'application/json','X-Signature':hmac.new(b'local-development-secret',b,hashlib.sha256).hexdigest()}); print(urllib.request.urlopen(r).read().decode())"
```

Запрос генерации: `POST /generate` с JSON `{ "user_id": 1, "model_slug": "image-fast", "prompt": "...", "ref_images": [] }`. Используйте `GET /tasks/{task_id}` для статуса и `GET /users/{id}/balance` для баланса с последними движениями журнала. В локальном стенде секрет задан как `local-development-secret`; задайте свой `WEBHOOK_SECRET` перед использованием вне разработки.

## Миграции

При старте контейнера API выполняется `python -m app.migrate` до запуска четырёх worker. Мигратор применяет по порядку SQL-файлы из `migrations/` один раз, записывая имя каждого файла в `schema_migrations`. Чтобы добавить миграцию, создайте следующий файл, например `migrations/002_add_feature.sql`, добавьте SQL и перезапустите сервис (`docker compose up --build`). Применённые миграции не редактируйте.

## Тесты

Сначала запустите БД, затем установите проект с тестовыми зависимостями и примените миграции:

```sh
docker compose up -d db
python -m pip install -e '.[test]'
$env:DATABASE_URL='postgresql://app:app@localhost:5432/generation'
python -m app.migrate
pytest -q
```

Тесты используют выделенную базу, очищают таблицы перед каждым сценарием и не предназначены для запуска на рабочей базе.

## Согласованность и сбои

Все изменения баланса и соответствующая строка `ledger` выполняются в одной транзакции PostgreSQL. Для пополнения первичен уникальный `payments.payment_id`; конкурентные повторы вставляют одну оплату и только победившая транзакция добавляет запись и баланс. Для списания транзакция блокирует строку пользователя, резервирует цену и пишет уникальную операцию с `reference=task_id`. Задача блокируется `FOR UPDATE`, когда принимается отказ или возврат; переход из `processing` терминален, а возвратный журнал имеет уникальность `(kind, reference)`. Поэтому конкурирующие отказы и таймауты могут зафиксировать не больше одного возврата. Баланс не меняется отдельно от записи журнала.

Если процесс падает до фиксации транзакции вебхука, PostgreSQL откатывает её, и провайдер может безопасно повторить webhook. Если падение произошло после фиксации, повтор увидит уже терминальное состояние/уникальный ключ и не спишет/не начислит повторно. Отправка провайдеру выполняется после фиксации попытки; падение между этими действиями оставляет попытку `sending`. В текущей версии такие неопределённые отправки не переотправляются автоматически: их необходимо разбирать операционно, чтобы не создать дубликат внешней генерации.

Сторож получает PostgreSQL advisory lock на отдельном соединении, поэтому таймауты обрабатывает только один из четырёх процессов. Он переводит истёкшую попытку через тот же сериализованный переход, что и webhook.

### Поздний результат после сторожа

Решение — считать срабатывание сторожа окончательным для конкретной попытки. Если все ноги исчерпаны и задача уже получила статус `failed` и возврат, поздний `completed` игнорируется. Результат и возврат одновременно не выдаются; пользователю не начисляется повторное списание и не меняется баланс. Если сторож лишь переключил задачу на следующую ногу, поздний callback старой ноги также не может завершить задачу: завершать её может только текущая попытка со статусом `waiting`. Это правило реализовано проверкой состояния задачи и попытки под блокировкой строки задачи.

## Настройки фейковых провайдеров

Провайдеры по умолчанию завершают задачу через случайные 2–20 секунд. Для экспериментов можно задать контейнеру провайдера `FAILURE_RATE` от 0 до 1, `FAILURE_TYPE` (`technical`, `moderation`, `payload`), `SYNC_MODE` (`503` или `timeout`), `WEBHOOK_DELAY`, `NEVER_CALLBACK=true` и `DUPLICATE_CALLBACK=true`. Параметры относятся к каждому контейнеру alpha/beta отдельно. `PROVIDER_TIMEOUT` задаётся в секундах для API.
